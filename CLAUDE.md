# CLAUDE.md

This file provides guidance to Claude Code when working with code in this repository.

## Running the Application

```bash
uv run hatty                          # Run with default config
uv run hatty -c /path/to/config.yaml  # Run with custom config
uv run hatty --debug                  # Enable Textual debug logging to debug.log
uv run hatty --demo                   # Run offline against curated fake data (no HA needed)
```

`--demo` boots the app with no config/HA connection, serving a curated fake dataset from
`src/hatty/demo/` (entities across every domain, a device/area registry backing the device tree `D`,
pre-seeded lists/dashboards/saved graphs, generated history). It's fully interactive — toggling a switch or nudging a thermostat visibly updates, because
`DemoHAClient` echoes each `call_service` back as a `state_changed` event — but a static snapshot (no
background ticker) that writes nothing to disk. Injected at the same `HACLI._client_factory` seam the
test suite's `FakeHAClient` uses; `DemoHAClient` is signature-parity-tested against `HAClient`.

`uv run hatty` uses the console script from the editable install, so no `PYTHONPATH`/`.venv` activation is needed. The `--debug` flag sets `TEXTUAL_LOG=debug.log`/`TEXTUAL_LOG_LEVEL=DEBUG` for the run.

`sbin/record-demo.sh` records a scripted screencast of `--demo` into `docs/demo.cast` + `docs/demo.gif` (embedded in `README.md`): it drives the TUI via `tmux send-keys` under `uvx asciinema rec` and renders the GIF with `agg` (auto-downloading the prebuilt aarch64 binary to `dist/` when not on PATH). The keystroke choreography is a plain sequence of `key`/`type` helpers near the bottom of the script — re-run it to regenerate the media after UI changes, tuning the `sleep` pacing as needed.

Dependencies are managed by **uv** (`pyproject.toml` + committed `uv.lock`; no requirements.txt): `uv sync` creates/updates `.venv` with the dev group (pytest, ruff, pyinstaller). The project is a real package — dist name `hatty`, import package `hatty`, console script `hatty` (`hatty.cli:main` — a thin entry that applies `--debug` before importing the Textual app). `uv build` produces sdist+wheel; `sbin/build-binary.sh` builds the PyInstaller standalone (`hatty.spec`). Nothing is published to PyPI yet.

Test suite: `pytest` (or `pytest tests/unit` for fast unit-only runs, no Textual app boot required).

hatty is an independent reimplementation of `../ha-cli`'s BUILD_PLAN.md spec — same conventions, separate codebase, not a port of ha-cli's source.

## Architecture

```
User Keybindings → HACLI (main.py) → HAClient (client.py) ↔ Home Assistant WebSocket
                                          ↓
                         _update_entities_display() → EntitiesTable
```

### Core modules (`src/hatty/`)

- **`main.py`** — The `HACLI` Textual app. Handles keybindings, routes incoming HA WebSocket messages via `handle_ha_message` (a `_HA_MESSAGE_HANDLERS` msg-type → `_on_ha_*` handler table), and debounces UI refreshes through `_schedule_display_update`/`call_later`. Owns the entity-table state (`all_entities`, `entity_registry`, `entity_names`, `search_term`, `columns`) plus cross-cutting plumbing: `spawn(coro)` (tracked fire-and-forget tasks — never use bare `asyncio.create_task`), `persist(*keys)` (mirror a collection into `app_config` + schedule the async save), the `graph_hours` property, `find_entity`, `dispatch_service_call`, `toggle_entity`. Entity-control service data is built by pure per-domain functions in the module-level `_CONTROL_SERVICE_BUILDERS` table.
- **`controllers/`** — the domain state lives on four controllers instantiated in `HACLI.__init__` with an injected app reference: `lists.py` (`ListController`, `app.list_ctl`: entity lists, current/default/last list, undo/redo), `dashboards.py` (`DashboardController`, `app.dash_ctl`: dashboards + all slot editing/split/span mutations, temp list-preview dashboards), `graphs.py` (`GraphController`, `app.graph_ctl`: `entity_history`/`climate_history` stores + `_trim_history`, detail-panel rendering, saved graphs, `is_graphable`/`is_climate_entity`/`is_binary_entity`, `history_fetcher`), and `connection.py` (`ConnectionController`, `app.conn_ctl`, issue #166: the HA websocket message pump — `handle_ha_message`, the `_HA_MESSAGE_HANDLERS` type→`_on_ha_*` table, and the `_handle_result_message`/`_handle_failed_result_message`/`_handle_event_message` handlers, owning only the `http_warned` one-shot guard). `HACLI.handle_ha_message` is a thin delegator to `conn_ctl` kept as the public client-callback seam; the pump reads/writes `all_entities`, the registries, and the pending-call machine through the app reference, and `_apply_name_override` stays on the app (shared with the rename path). **HACLI keeps its old attribute surface via property pairs** (`app.dashboards`, `app.current_list_name`, `app._detail_entity_id`, …) so screens and tests read/assign through the app unchanged; UI code calls controllers directly (`self.app.dash_ctl.set_slot(...)`).
- **`const.py`** — single home for shared constants (`TOGGLABLE_DOMAINS`, `CONTROLLABLE_DOMAINS`, `WIDGET_TYPES`/`WIDGET_TYPE_DOMAINS`, `BINARY_STATE_MAP`, `DEFAULT_COLUMNS`, `DEFAULT_GRAPH_HOURS`); imports nothing from the app, so it's always cycle-safe. `MEDIA_FEAT` + `media_supports(features, flag)` hold the `media_player` `supported_features` bitmask (HA's `MediaPlayerEntityFeature`) used to capability-gate `controls/media_player_screen.py`'s fields/buttons.
- **`client.py`** — `HAClient`: async websocket auth handshake, `get_states`/`subscribe_events`/`config/entity_registry/list`/`config/entity_registry/update`/`config/device_registry/list`/`config/device_registry/update`/`config/area_registry/list`/`call_service` requests sent through `_send` (id-assignment + `pending_requests: dict[id, str]` tracking), and the REST history/logbook fetchers built on `_get_json` + `_fetch_raw_history` (climate passes `minimal=False` to keep attributes). REST helpers swallow errors and return `None`. The device/area registries back the device tree view (issue #124); `update_device_registry(device_id, area_id)` reassigns a device to an area, and `create_area(name)`/`rename_area(area_id, name)` (`config/area_registry/create`/`update`, issue #146) manage areas themselves.
- **`config.py`** — `load_config`/`save_config`. Errors are returned as `{"error": ...}` data, never raised. `_migrate_legacy` moves the old `favorites` key to `lists` and wraps a bare-list `lists` value into `{"default": [...]}`; defaults come from `default_config()` in one place.
- **`terminal_title.py`** — `apply(title)`/`restore(prev)` set (and, on exit, revert) the terminal/tmux window title per the `terminal_title_enabled`/`terminal_title` config keys (default: on, `"hatty"`). Always writes the OSC 2 escape sequence (any terminal, plus tmux's `pane_title`); when `$TMUX` is set it also shells out to `tmux rename-window` for the status-bar window name, capturing the prior name + `automatic-rename` setting so `restore()` can put both back. All tmux calls go through `_run_tmux`, which swallows any subprocess failure — a title is cosmetic and must never affect startup/shutdown. Wired in `main.py`'s `_apply_config`/`_apply_terminal_title` (shared by the real/demo/onboarding boot paths), `on_unmount` (restore), and `_on_config_saved` (restore + re-apply so a live edit takes effect immediately).

### UI components (`src/hatty/ui/`)

- **`entity_table.py`** — `COLUMNS` registry (key → header + extractor; `DEFAULT_COLUMNS` lives in `const.py`), sort order (in-list entities first, then alphabetical by friendly name within each group), cursor position restored across rebuilds by `entity_id` row key. `get_display_name(entity)` is the single source of truth for an entity's displayed name (local override via `entity["_local_name_override"]`, falling back to HA's `attributes.friendly_name`, then `entity_id`); used by the table, search/sort, the detail panel, and the control popup. `is_dead(entity)` (state `unavailable`/`unknown`, `DEAD_STATES`) drives a shared dim treatment (#148): dead entities' table cells are wrapped in a `dim` Rich `Text` (both the fast in-place `update_cell` path and the full rebuild), and the device tree dims its leaf labels via the same predicate.
- **`graph/entity_detail.py`** — Sparkline/plot history panel, hidden unless the `-visible` CSS class is set. For numeric entities it cycles Max/Min/Mean sparkline summaries plus Line/Scatter plotext modes (`t`), and can overlay comparison entities added via `+` (`action_add_to_graph`, blocked for climate entities in either direction). `climate` entities instead render through `update_climate`/`_render_climate_mode`: a fixed dual-line (current vs. target temperature) plot with a heating/cooling marker strip from `hvac_action`, bypassing the generic mode-cycling entirely. `binary_sensor` entities render through `update_binary`/`_render_binary_mode` (also mode-cycling-free): a square-step off/on timeline built by `ui/graph/binary_history.py`'s `to_step_points` (with the final state extended to "now"), a fixed off/on y-axis, and a `binary_stats` line (% on, change count, last state). Binary history flows through `HAClient.fetch_binary_history` (on/off → 1/0, drops unavailable/unknown; `GraphController.history_fetcher` picks the fetcher per entity) into the same `entity_history` store, and `_record_state` maps live binary state changes the same way. Binary and numeric entities can't be mixed in one comparison graph (`action_add_to_graph` refuses both directions); binary+binary comparisons are fine.
- **`graph/preview_screen.py`** — `GraphPreviewScreen`, the fullscreen graph opened with `G`, mirroring `graph/entity_detail.py`'s numeric-vs-climate split (`_update_display`/`_update_climate_display`). Takes a list of `entity_ids` (comparison graphs), a `colors` dict (`entity_id` → `plotext` color name; `tab` picks the active line, `c` cycles its color through the default palette, `C` opens `graph/color_popup.py`'s `GraphColorPopup` — an `OptionList` over the full plotext named palette with Rich-markup swatches), and an optional `saved_graph_name` (adds the `u` update-in-place footer action alongside `S` save-as when set, and prefills `SaveGraphNamePopup` with the saved name). Tracks `_window_end`/`_live_anchor` for `left`/`right` history paging via `HAClient.fetch_history`/`fetch_climate_history`'s `end` parameter — `None` means anchored to "now" with live `state_changed` refreshes; paging away from live suppresses those until paging forward reaches the original anchor. `left`/`right` page by *half* a window (consecutive pages overlap 50% for visual continuity); `shift+left`/`shift+right` page by `_FAST_PAGE_MULTIPLIER` (6) full windows; `_page_back`/`_page_forward` hold the shared paging logic parameterized by `hours` so both strides go through the same live-anchor bookkeeping. `+`/`-` zoom the window span via `_local_hours`, a screen-local override of the global `graph_hours` (never persisted to config, but `S`/`u` save it via `_window_hours()`); zooming always freezes the window (`_window_end` set), zoomed windows never re-enter live mode when paging forward (they pin at `_live_anchor`), and `home` (`action_snap_live`) clears the zoom and reloads live. The title carries a `_window_status()` badge: `[LIVE]`, `[⌕ 2h]` when zoomed, `[◀ 6h back]` when paged. On a comparison graph the non-cursor stats line (min/avg/max/unit) always describes the `tab`-selected active entity rather than only the first one, and is prefixed with that entity's name. `enter` toggles cursor/inspect mode (`_cursor_mode`/`_cursor_index`, disabled for climate/empty graphs): drops a `plt.vline` at the selected sample and swaps the stats line for every plotted entity's nearest value at that timestamp (`_nearest_value`), and repurposes `left`/`right`/`shift+left`/`shift+right` to move the marker (by 1 or by `_FAST_PAGE_MULTIPLIER`) instead of paging.
- **`graph/plot_time.py`** — pure x-axis time helpers shared by `graph/entity_detail.py` and `graph/preview_screen.py`: `ts_to_hhmm`/`ts_to_full` label formatting and `time_axis(t0, total_secs)`, which returns tick positions/labels plus day-boundary positions. Windows ≤24h keep the even 6-tick hh:mm axis; longer windows tick at (thinned) local midnights labeled `Jul 02` and every midnight gets a gray `plt.vline` day-change guide. Midnights come from `midnights_between`, which re-localizes each calendar day rather than stepping 24h, so DST days keep their wall-clock midnight.
- **`graph/plot_render.py`** — the shared plotext rendering layer used by `graph/entity_detail.py`, `graph/preview_screen.py`, and `dashboard/widgets/graph.py`: `PLOTEXT_MODES`, `DEFAULT_COLOR_PALETTE`, `plot_width`, `earliest_t0`, `apply_time_axis`, `plot_numeric_series` (min/max downsample + line/scatter), `set_binary_axis`, `numeric_stats_line`, and `render_climate` (the full Current/Target + hvac-strip plot). New graph surfaces should compose these instead of hand-rolling plotext calls.
- **`graph/duration_popup.py`** — `GraphDurationPopup`, opened by `T`. A `RadioSet` of presets (1h/4h/12h/24h/48h/1 week) plus free-text Hours/Minutes `Input`s that override the radio selection with a computed custom `float` when either is filled in. Shared by the small panel, fullscreen graph, and dashboard Graph widgets via the single global `graph_hours` config value.
- **`config_screen.py`** — `ConfigScreen`, pushed only via the "Configuration" command-palette entry (no direct keybinding). A scrollable form over the raw config dict: connection (URL/token, `o` shells out to `$EDITOR`/`nano`, `v` unmasks the token `Input`), theme/default graph type/default graph timeframe `Select`s, a terminal/tmux title toggle + text `Input` (`terminal_title_enabled`/`terminal_title`, applied via `hatty/terminal_title.py`), the same column-visibility `SelectionList` as `column_config_popup.py`, and read-only Lists/Entity Name Overrides/Dashboards/Saved Graphs count summaries (editing those collections stays in their own popups — `l`/`r`/`d`/`s`). `s`/`ctrl+s` calls `config_module.save_config` and dismisses with the new config dict; `escape` dismisses with `None`.
- **`list_selection_popup.py` / `.css`** — Favorites-list management modal. Reads `list_names`/`default_list_name` off `self.parent` (the host `HACLI` app). `Shift+↑/↓` reorders the lists collection itself (issue #212, mirrors `ColumnConfigPopup`'s column reorder) via `ListController.reorder_lists`; the synthetic "View All" row at index 0 can't be moved, and reordering is refused with a notify while a search filter is active (the visible order is then a filtered subset). Reordering relabels the existing `ListView` rows in place (`ListPopup._relabel`) rather than clearing and re-appending, since setting `.index` right after a clear+append can post a `Highlighted` message referencing a `ListItem` whose `Label` child hasn't finished mounting yet.
- **`column_config_popup.py`** — Column visibility modal; imports `COLUMNS` from `entity_table.py`.
- **`controls/control_popup.py`** — handles `CONTROLLABLE_DOMAINS` (see `const.py`) minus lights and media_player; builds per-domain input fields with a Save/Cancel model (`enter` saves, dismissing with the collected values for `HACLI.dispatch_entity_control`/`_CONTROL_SERVICE_BUILDERS`). Lights and media_player are *not* handled here — `main.py` routes them to `controls/light_screen.py`/`controls/media_player_screen.py` before this popup is considered. For `input_number`, the nudge step comes from each field's own `step` attribute (tracked in `_field_steps`) rather than a flat ±1, so it matches whatever increment Home Assistant was configured with.
- **`controls/light_screen.py`** — `LightControlScreen`, the dedicated light control pushed by `e` on a light. Live-apply model: every change is queued (`_queue`) and dispatched through `HACLI.dispatch_entity_control` after a 0.3s debounce — there is no Save/Cancel, `escape` flushes and closes. Layout: title with power state (`space` toggles via `light.turn_on/turn_off`, a priority binding so focused Buttons don't swallow it; `check_action` releases it while the effect-filter `Input` is focused), live color/brightness preview bar, always-visible Brightness slider, then a `TabbedContent` with only the supported tabs — White (`KelvinSlider` + Warm/Neutral/Cool presets on `1`/`2`/`3`), Color (swatch buttons + `ColorPickerModal` via `p`), Effects (filter `Input` + `OptionList`, selection applies immediately). `t` cycles through the composed tabs with wraparound (released while the effect filter is focused, hidden when only one pane exists; landing on Effects deliberately does *not* focus the filter so the next `t` keeps cycling), and `left`/`right` switch panes natively when the `Tabs` header is focused — the screen's `on_key` hijack exempts `Tabs` alongside `Input`/sliders, so left/right otherwise adjust a focused slider's value or cycle within the `#color_swatches`/`#white_presets` Horizontal button rows (wrapping at the ends, via `_enclosing_row`/`_focus_within_row`). `up`/`down` are a separate priority `nav_focus(±1)` binding (issue #286) that always *moves focus* rather than being swallowed by a focused slider's own arrow handling — one step at a time normally, or skipping a swatch/preset row as a whole block via `_focus_out_of_row`; `check_action` releases it while the effects `OptionList` is focused so its own up/down cursor movement still works. Capability detection reads `supported_color_modes` (fixed capability, present while off — unlike `brightness`/`color_temp` which only appear while on); the initial tab follows the live `color_mode`. Since only the touched field is queued, white/color never send a conflicting `kelvin` + `rgb_color` pair. Kelvin helpers tolerate legacy mireds-only attrs (`_read_kelvin`/`_read_kelvin_range`); `hsv_to_rgb` and the preset/swatch tables live here too.
- **`controls/media_player_screen.py`** — `MediaPlayerControlScreen`, the dedicated media_player control pushed by `e` (issue #210), modeled on `controls/light_screen.py`'s live-apply model: no Save/Cancel, `escape` flushes any pending debounced field then dismisses. Every control is capability-gated by `const.media_supports(attributes.supported_features, flag)` against HA's `MediaPlayerEntityFeature` bitmask (`const.MEDIA_FEAT`) — unsupported controls simply aren't composed. Layout: title with state glyph + now-playing (`media_title`/`media_artist`); a `PercentageSlider` volume field (0–100 ↔ `volume_level` 0.0–1.0, debounced through `_queue`/`_flush` into `HACLI.dispatch_entity_control` exactly like the light screen's brightness slider); a transport `Horizontal` of Previous/Play-Pause/Stop/Next buttons, each shown only when its feature bit is set, dispatching directly via `HACLI.dispatch_service_call` (`media_previous_track`/`media_play_pause`/`media_stop`/`media_next_track`) with an optimistic title flip; `Select` fields for `source`/`sound_mode` (immediate dispatch on change, guarded against the `Select.Changed` HA/Textual posts for its own initial value on mount); and Shuffle/Repeat toggle buttons (repeat cycles off→all→one). `space` (priority binding) play/pauses; `s` is bound to stop and gated off via `check_action` when the feature bit is absent (so the footer never advertises an unsupported control). Previous/Next have no dedicated key — they're only reachable by focusing their button and pressing enter. `left`/`right` are instead pure focus navigation (an `on_key` hijack mirroring `light_screen.py`'s `t`/#88 pattern): they cycle within the `#transport_buttons`/`#toggle_buttons` rows (wrapping, `_focus_within_row`) and otherwise walk the focus chain, exempting the volume `PercentageSlider` (which keeps left/right as its own value-adjust) and an expanded `Select`'s overlay (an `OptionList`, native cursor movement). `up`/`down` (issue #291, mirrors `light_screen.py`'s #286 fix) are a priority `nav_focus(±1)` binding that always steps the focus chain the same way — so a focused volume slider never swallows them as value changes; `check_action` releases `nav_focus` while the `Select` overlay is focused. The `#transport_buttons`/`#toggle_buttons` rows are also row-aware for `up`/`down` like `light_screen.py`'s swatch/preset rows (`_enclosing_row`/`_focus_out_of_row`): `up`/`down` enter a row at its first/last button but skip the rest of the row as a block once inside it — Shuffle/Repeat (no dedicated hotkey) stay individually reachable by entering the row from either end.
- **`onboarding_screen.py`** — `OnboardingScreen`, the first-run wizard. `main.py`'s `on_mount` pushes it (instead of dead-ending on an error sub_title) when `config.needs_onboarding(app_config)` is true: no config file, or a missing/empty/placeholder (`YOUR_LONG_LIVED_ACCESS_TOKEN`) url/token. A *parse* error is left alone so a hand-edited-but-broken file is never silently overwritten. Collects URL + long-lived token (with token-creation instructions and `ctrl+v` unmask), `ctrl+t` runs a read-only `client.probe_connection` (a one-shot `GET /api/config` reporting the HA version or a bad-URL/bad-token reason), `ctrl+s`/Save dismisses with `{"url", "token"}`. `main.py._on_onboarding_done` merges those over `config.default_config()`, `save_config`s it (creating the XDG dir), and calls `_start_client()` — no restart. Re-runnable later via the "Setup wizard" command-palette entry (`action_show_onboarding`). Startup is factored into `_apply_config(cfg)` (state population) + `_start_client()` (retires any old client, then launches the retry loop) so the onboarding and normal paths share one seam.
- **`search_input.py`** — Custom `Input` posting `SearchSubmitted`/`SearchChanged` messages.
- **`dashboard/screen.py`** — `DashboardScreen`, a full (non-modal) `Screen` pushed via `d`, not a popup. Renders a `Grid` of `DashboardSlotWidget` containers (one per `rows * cols` cell, each wrapping the live content widget from `build_slot_content`) for the dashboard named `self.parent.current_dashboard_name`. Arrow keys move a selection cursor, `e` opens the slot's entity controls (mirrors the main table/device tree `e` — issue #216), `E` enters edit mode, `a` opens `DashboardSlotPopup` to assign a slot's widget type + entity, `delete` clears it, `enter` toggles, `d` opens `DashboardSelectionPopup`, `D` opens the device/area tree (issue #216), `l` jumps straight back to the last-shown/default list (`HACLI._list_jump_target`), only opening `ListSelectionPopup` when no list exists yet — *except* when the selected slot's content widget (found via `_content_widget_at_cursor`) is a `ThermostatSlotWidget`, `PanelSlotWidget`, `FanSlotWidget`, or `MediaPlayerSlotWidget`, all of which repurpose these keys for in-widget interaction instead of grid navigation/toggling: a `ThermostatSlotWidget` intercepts `up`/`down` in `action_move_cursor` to call `widget.adjust_setpoint(...)` (setpoint is the one thing that needs in-place arrow-key control); a `PanelSlotWidget` intercepts `up`/`down` to move its own internal row cursor (`widget.move_cursor(...)`) and intercepts `enter` in `action_toggle_slot` to call `widget.toggle_selected()` on whichever row is highlighted; a `FanSlotWidget` intercepts `up`/`down` to call `widget.adjust_speed(...)`, toggling power via `HACLI.toggle_entity` on `enter` instead; a `MediaPlayerSlotWidget` (issue #210) intercepts `up`/`down` for `widget.adjust_volume(...)` *and* `left`/`right` for `widget.previous_track()`/`widget.next_track()` (the only widget that repurposes horizontal movement too — `action_move_cursor` returns before `_move_selection` so the grid cursor doesn't also step), and `enter` play/pauses via `HACLI.toggle_entity` (whose `media_player` carve-out sends `media_play_pause`, mirroring the fan/switch on-off toggle). `left`/`right` always navigate the grid normally for every other widget type. `refresh_entity(entity_id, entity, pending)` (called from `main.py`'s `_refresh_dashboard_widgets`) re-renders any matching `EntitySlotWidget` in place, and also forwards to any `PanelSlotWidget` whose `entity_ids` contains that entity.
- **`device_tree_screen.py`** — `DeviceTreeScreen` (issue #124), a full (non-modal) `Screen` pushed via `D`, wrapping a Textual `Tree[dict]`. Three grouping modes cycled by `v` (view; shown in a `#device_tree_status` line): **device** (flat Device → Entity), **area** (nested Area → Device → Entity), and **integration** (nested Integration → Device → Entity, keyed off the entity registry's `platform` field — issue #147). The synthetic `Devices`/`Areas` root node is hidden (`show_root=False`, issue #144). They're built by the pure module-level `build_device_groups(entity_registry, device_registry)` / `build_area_groups(entity_registry, device_registry, area_registry)` / `build_integration_groups(entity_registry, device_registry)` — HA areas contain *devices* (device.`area_id`), not entities, so area mode walks area → device → entity; integration mode partitions entities by `platform` then groups each into Device → Entity; devices/entities without an area/device/platform fall into `UNASSIGNED_LABEL`/`NO_DEVICE_LABEL`/`NO_INTEGRATION_LABEL` buckets. Areas/integrations collapse by default (only auto-expanding under an active filter — issue #145); `x`/`X` collapse-all/expand-all the whole tree (issue #143). Each node's `data` dict is tagged `kind` = area/integration/device/entity. `/` opens an embedded `SearchInput` (same `event.stop()` + local-refilter pattern as `dashboard/slot_popup.py`) that live-filters the tree via the pure `filter_device_groups`/`filter_area_groups`/`filter_integration_groups` helpers, all taking a `scope` param (issue #140): an entity matches by `entity_matches` (name/entity_id/state), a device whose label matches keeps all its entities (otherwise only matching ones), an area/integration whose label matches keeps its whole subtree; a scope selector cycled with `ctrl+s` (all/area/device/entity/integration, reflected in the placeholder + status line) restricts *which* node level the term matches (`all` = the blended default; `integration` matches integration/platform labels in integration mode — issue #180). Device nodes auto-expand while filtering and `escape` clears the filter before closing the screen. While a filter is active the status line appends `Filter: '<term>' — N entities` (N = surviving entity leaves counted from `_entity_nodes`, which `rebuild()` fills before re-rendering `_status_text`), and an all-pruned tree gets a single dim `— no matches —` placeholder leaf (`kind: placeholder`) so it's never silently blank (issue #149). `enter` on an entity leaf toggles it or, for a non-togglable domain, falls back to opening its controls (`app.toggle_or_open_controls(entity_id, fullscreen_graph_fallback=True)`, via `on_tree_node_selected` — issue #150); `e` on an entity leaf opens the same controls as the main table via `app.open_entity_controls(entity_id, fullscreen_graph_fallback=True)` — the kwarg makes the graphable-fallback push the fullscreen `GraphPreviewScreen` instead of the main table's detail panel (invisible behind a pushed screen); `G` on a graphable entity leaf pushes the fullscreen `GraphPreviewScreen` directly (`g` is unbound here — grouping moved to `v`); `space` on an entity leaf toggles list membership (a priority binding since the focused `Tree` binds `space` to fold — non-entity nodes forward to `action_toggle_node`, and the screen's own `check_action` releases it while the search `Input` is focused): the target is `current_list_name` falling back to `list_ctl.jump_target()` *without* switching the main table's selection, with `ListSelectionPopup` only when no list exists; ## Config file structure

Search order: explicit `-c` path → `~/.config/hatty/config.yaml` → `./config.yaml`.

**Two-tier persistence (issue #63).** The YAML is *lean* — it carries only connection settings and display preferences. The user-data collections (`lists`, `entity_names`, `dashboards`, `saved_graphs`, `manual_lists`, `default_list`, `default_dashboard`) live in a SQLite DB (`src/hatty/storage.py`, `Storage`) at `<config dir>/hatty.db` (or `$XDG_DATA_HOME/hatty/hatty.db` when there's no config path). `storage.COLLECTION_KEYS` lists exactly those keys. On boot, `HACLI._open_storage(cfg)` opens the DB and, the first time (empty DB), imports any collections still in the YAML (one-time migration), then loads the DB collections back over `cfg` so **SQLite is authoritative**. `_save_config_async` writes the lean YAML (collection keys stripped) *and* `Storage.save_all(...)` via `asyncio.to_thread`; `ConfigScreen` strips the same keys from the YAML it writes but keeps them in the dict it dismisses. `Storage` keeps the in-memory dict *shapes* the app already used — it's only the load/save boundary, replacing each collection wholesale in one transaction. The app still holds `app_config` as the working copy; `action_show_config` passes the live `app_config` (not a fresh YAML load) so counts render and its save doesn't drop collections.

```yaml
home_assistant:
  url: "http://homeassistant.local:8123"
  token: "YOUR_LONG_LIVED_ACCESS_TOKEN"
columns: ["name", "value", "last_changed", "in_list"]
theme: null
graph_type: line
graph_hours: 4
terminal_title_enabled: true
terminal_title: hatty
```

The collection shapes below now describe the SQLite rows (see `storage._SCHEMA`), not YAML keys, but the in-memory dicts are unchanged:

`dashboards` is a dict keyed by dashboard name, each with `rows`, `cols`, and a flat `slots` list of `{row, col, widget_type, entity_id}` (only occupied cells are stored). A `panel`-type slot additionally carries `entity_ids: [...]` (its `entity_id` is `None`), and a `gauge`-type slot may carry optional `gauge_min`/`gauge_max` overrides — every other widget type leaves those keys out entirely, so existing configs are unaffected. Any slot may carry optional `row_span`/`col_span` ints (absent = 1): its *footprint* covers `rows[row, row+row_span) × cols[col, col+col_span)`. The pure helpers in `ui/dashboard/layout.py` (`footprint`/`slot_covering`/`fits`/`exceeds_bounds`) define coverage, overlap, and bounds; `HACLI._resize_dashboard_slot` persists span changes (dropping the keys at 1 so unspanned slots keep the legacy shape), `_swap_dashboard_slots` refuses span-aware misfits (returns `bool`), and `_resize_dashboard` prunes by footprint, not just anchor. A `split`-type slot (issue #81, Approach B) carries a `children` fragment `{rows, cols, slots: [...]}` — a nested mini-grid local to that pane; child slots are plain slot dicts with coords relative to the child grid, may not span or nest further (validated/ignored by `ui/dashboard/widgets/split.py`'s `normalized_children`, never crashed on), and the split slot's own `entity_id` is `None` while its top-level `row_span`/`col_span` still apply. The slot-editing helpers in `main.py` (`_set_dashboard_slot`/`_clear_dashboard_slot`/`_update_panel_entity_ids`/`_swap_dashboard_slots`) take an optional `parent` anchor resolved through `_dashboard_grid_ctx` to target a split's child grid instead of the dashboard's own `slots`. `current_dashboard_name` is in-memory only, not persisted; `default_dashboard_name` (config key `default_dashboard`) is persisted, mirroring `default_list_name`/`default_list`, and is used as the fallback target when no dashboard has been shown yet this session.

`saved_graphs` is a dict keyed by graph name, each value `{entity_ids: [...], graph_type: "line"|"scatter", hours: <float>, colors: {entity_id: color_name}}` — `entity_ids` has one entry for a single-entity graph or several for a comparison graph (see `GraphPreviewScreen`/`action_add_to_graph`'s `+` compare key). `colors` is optional (omitted when every entity kept its default palette color) and maps each `entity_id` to a `plotext` color name, set via `GraphPreviewScreen`'s `tab` (pick active line) + `c` (cycle its color) / `C` (color-picker popup) bindings.

`manual_lists` (issue #213) is a set of list names currently in manual-sort mode, stored as a JSON array in the `meta` table (mirroring `default_list`/`default_dashboard`, not a dedicated table like `lists`). Every `entity_lists[name]` is always an ordered `list[str]`, but `EntitiesTable._get_sorted_entities` only honors that order for a list in `manual_lists` — otherwise it re-sorts alphabetically by display name (today's default, "no sort"). `ListController.reorder`/`set_manual`/`disable_manual` own the mode; a list's first `Shift+↑/↓` reorder freezes its current *visible* order and switches it to manual (`ListController._freeze_visual_order`), while toggling manual off and back on (`o`) never re-freezes — it just flips the flag, so a curated order survives a round trip through alphabetical display.

## Key behaviors

- `/` search (the sub_title appends a `visible/total` match count via `set_title_based_on_focused_ui`, issue #149), `space` toggle list membership, `shift+up`/`shift+down` move the highlighted entity within the active list (issue #213 — refused with a notify when no list is selected or a search is active, since the visible order wouldn't be list-scoped), `o` toggle that list between manual order and alphabetical ("no sort", today's default), `r` rename entity (local override or push to HA), `l` list popup, `c` column config, `g` graph panel, `G` fullscreen graph, `s` saved graphs popup, `e` edit attributes (lights get the live-apply `LightControlScreen`; media_player the live-apply `MediaPlayerControlScreen`; fan/climate/cover/lock/input_number the Save/Cancel popup), `d` dashboard view, `D` device/area tree view, `escape` back/clear, `ctrl+q` quit (issue #278 — deliberately not a bare `q`, to avoid tearing down the whole TUI on a stray keystroke). **List lock (issue #214):** viewing a list is locked by default (🔐 in the sub_title, `set_title_based_on_focused_ui`) — pressing `space` to remove a member while locked pushes a `ConfirmPopup` ("Unlock '<list>' to remove items?") instead of removing; confirming unlocks the list *for the session* (🔓) and removes that one item, after which further removals go through freely until the list re-locks. `L` toggles the lock manually (`ListController.lock`/`unlock`/`is_locked`, mirroring the `o` sort-toggle pattern). The lock is entirely transient — never persisted, and reset (re-locked) every time the list is (re)entered via `select_or_create` — and only gates *removals* in pure list-view; adding a member, and any add/remove while a search filter is active (the "filter list for adding items" path), are never gated since a searched view isn't list-scoped. Undo/redo (`u`/`ctrl+r`) bypass the lock entirely so they always work. The device tree mirrors the main-table keys as screen-local bindings (`/` search, `e` opens controls — issue #216, `G` graph, `space` list toggle, `l` lists, `d` dashboard, `?` help) plus its own `v` view/grouping cycle, `ctrl+s` search scope, `x`/`X` collapse/expand-all, `m` move device, `i` device/entity info, `n` area→dashboard quick-create, and `a`/`r` create/rename area (the last three area mode only). Toggling a switch/light itself is `enter` on the entities table (`on_data_table_cell_selected`), not a dedicated key; `enter` on `media_player` sends `media_play_pause` (a `TOGGLABLE_DOMAINS` carve-out in `HACLI.toggle_entity`, since its state is playing/paused/idle rather than on/off); `enter` on a *non-togglable* entity (e.g. `lock`, safety-sensitive — issue #215) falls back to opening its controls (shared `HACLI.toggle_or_open_controls`, issue #150) on both the table and the device tree.
- Fullscreen graph (`G`, `GraphPreviewScreen`): `t` cycles plot type, `left`/`right` scroll through history half a window at a time (re-entering live mode when paging forward past "now"), `shift+left`/`shift+right` page by 6 full windows for covering long ranges quickly, `+`/`-` zoom the visible span in/out (screen-local, doesn't touch the global `graph_hours`), `home` snaps back to the live view and clears any zoom, `S` saves the current entity set/plot type/duration/colors under a name via `SaveGraphNamePopup` into `saved_graphs`, `u` updates the saved graph in place instead when the screen was opened from one. `tab` cycles the active comparison entity, `c` cycles that line's color through the default palette, `C` opens the full color-picker popup (`c`/`C` disabled for climate graphs); on a comparison graph the stats line's min/avg/max always reflect whichever entity `tab` last selected, not just the first one. `enter` toggles cursor/inspect mode, repurposing `left`/`right`/`shift+left`/`shift+right` to step a marker sample-by-sample (or by 6) instead of paging (unavailable for climate graphs). `s` at the main entity table opens `SavedGraphsPopup` to reopen/rename/delete a saved graph. `main.py`'s `check_action` denies a `_GRAPH_SCREEN_DENYLIST` of main-table-only actions (search, expand, rename, column config, activity/device log, graph toggles) while `GraphPreviewScreen` is active, so their bindings don't stay live (and visible in the footer) against the hidden table behind it — mirrors the existing `DashboardScreen` carve-out (only `quit` and `show_saved_graphs_popup` stay enabled there).
- Dashboard view (`d`): a full screen, not a popup — pushed via `push_screen` like the other screens but stays on the screen stack until `escape`. First entry auto-creates a "Main" 3x3 dashboard if none exist yet. Inside, Use mode: arrow keys move the grid cursor (skipping over a spanned slot's whole footprint), `enter` toggles the slot's entity, `e` opens the slot's entity controls (mirrors the main table/device tree `e` — issue #216), `r` renames it, `E` enters layout Edit mode. Both modes: `d` manage dashboards (create/select/rename/resize/delete), `D` opens the device/area tree (mirrors the main table — issue #216), `t`/`G` cycle plot type / open the fullscreen graph, `l` back to list. Edit mode: `a` assigns a slot's widget type + entity, `delete` clears a slot, `ctrl+arrows` grow/shrink the selected slot's `col_span`/`row_span` (refused with a notify when the footprint would overlap or leave the grid), grab-move (`enter`) moves the whole footprint and refuses misfitting drops, and every operation (assign/clear/rename) targets the slot covering the cursor regardless of which covered cell is selected; `escape` leaves edit mode before its usual back-out ladder. When the selected slot is a `thermostat` widget, `up`/`down` adjust its setpoint in place instead of moving the cursor. When the selected slot is a `panel` widget, `up`/`down` move a cursor *within* the panel's entity list instead, and `enter` toggles whichever entity is highlighted inside the panel (rather than the slot's own `entity_id`, which panels don't have). **Split panes**: `s` in edit mode splits the pane at the cursor into a local nested mini-grid (`SplitSlotPopup`: `v` left/right, `h` top/bottom, `q` quarters — the grid itself is untouched, unlike the old global refine); an existing widget moves into child (0,0). `enter` in Use mode descends into a split (the cursor becomes a path — `DashboardScreen._cursor_path`, with `cursor_row`/`cursor_col` properties over the tail), and in Edit mode — where `enter` is grab-move — `a` on a split descends instead of opening the assign popup ("split" isn't an assignable widget type; assignment targets a child cell, and `DashboardSlotPopup` falls back to the default type for any non-assignable `widget_type` rather than crashing the `Select` — issue #89). `escape` ascends one level before its usual back-out ladder, arrows navigate the child grid and never auto-ascend at an edge. All edit ops (assign/clear/grab-move/panel manage) work inside the child grid, child cells can't span (`ctrl+arrows` refused), and splits can't nest (one level max). **Cross-grid grab-move (issue #220)**: a grab is no longer confined to the grid it started in — while holding one, `a` on a split descends into it and `escape` ascends out of one *without* releasing the grab (only a top-level `escape` releases it), so a widget can be carried between the top-level grid and a split's child grid (or between two splits). Dropping on an empty cell moves the widget; dropping on an occupied cell swaps the two across grids (`DashboardController.move_slot_across`, alongside the existing same-grid `swap_slots`). A split itself can never land inside a child grid (would nest), refused with a notify and the grab left held. `u` in edit mode unsplits: a single surviving child collapses back into the slot; multiple occupied children are refused with a notify.
- Theme: Textual's built-in command palette (`Ctrl+P` → "Change theme") switches themes; the choice is persisted to the `theme` config key via `HACLI.watch_theme` and reapplied on the next launch (`main.py`'s `on_mount`).
- Command palette (`Ctrl+P`): `HACommandProvider` exposes three static entries regardless of how many lists/dashboards/saved graphs exist — "Configuration" (`action_show_config`, pushes `ConfigScreen`), "Lists" (`action_palette_switch_list`, jumps straight to the last-shown/default list, never opening `ListSelectionPopup`), and "Dashboard" (`action_show_dashboard`, opens the last-shown/default dashboard). Use the `l`/`d`/`s` keys for the full list/dashboard/saved-graphs picker popups. Each of these three handlers calls `HACLI.pop_to_base_screen()` before acting, so invoking them while another screen is pushed (dashboard, graph, config) pops back to the main table first instead of updating state behind a still-visible screen.
- **Connection resilience**: `HAClient.listen()` is a single retry loop that covers the *initial* connect as well as reconnects — if HA is unreachable at startup it keeps retrying with exponential backoff (`RECONNECT_DELAY` 5s → `MAX_RECONNECT_DELAY` 60s) instead of giving up, and the sub_title shows the retry status. A rejected token raises `AuthenticationError`, which stops the loop (retrying can't help) and surfaces an `ha_auth_failed` message telling the user to fix the token. The entity, device, and area registries are (re)fetched on every `ha_connected` (not once in `on_mount`), so reconnects refresh them. Connection state reaches the UI via `on_message` types `ha_connected`/`ha_connect_failed`/`ha_reconnecting`/`ha_disconnect`/`ha_auth_failed`, handled in `handle_ha_message`.
- **Popup styling**: every popup/widget uses inline `DEFAULT_CSS` (no external stylesheets). `ui/popup_base.py`'s `PopupScreen` carries the shared modal scaffolding (centering, the `.popup-container` panel box, `.popup-title`); `ListPopup` adds the name-list plumbing (populate with `*` default marker, `_item_name`) used by the list/dashboard/saved-graphs selection popups. New popups should subclass these and keep only their deltas in `DEFAULT_CSS`.
- `HAClient.connect()` returns early without raising if the first websocket message isn't `auth_required` — a known rough edge inherited from the original spec, not fixed here to stay spec-faithful.

## Testing

- `tests/unit/` — pure logic, no live Textual app required beyond a throwaway mounting harness for `entity_table.py`: `test_config.py`, `test_entity_table.py`.
- `tests/` (top-level) — acceptance tests booting the real `HACLI` app via Textual's `Pilot` and a `FakeHAClient` (see `tests/conftest.py`). No test touches a real Home Assistant instance — `FakeHAClient` fully replaces `HAClient` at the `app._client_factory` seam.
- Verifying against a real Home Assistant instance (auth handshake, real `call_service` effects, real history) is a manual step: fill in `~/.config/hatty/config.yaml` from `config.example.yaml` with a real URL and long-lived access token, then run `uv run hatty`.
- **Always ask before interacting with a real Home Assistant instance.** Running `uv run hatty` against `~/.config/hatty/config.yaml` (or any other real config) connects to live HA and can call real services — e.g. flipping a real switch — not just read state. Get explicit confirmation first, even for "just verifying the fix."
